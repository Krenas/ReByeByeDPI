# Правила проекта ReByeByeDPI

Версия: 1.1  
Дата: 2026-11-03  
Основа: оригинальный ByeByeDPI Android, GPL-3.0.

## 1. Цель

Развивать существующий проект ByeByeDPI Android, сохраняя его архитектуру, совместимость, авторские сведения и лицензионные обязательства.

## 2. Обязательные требования продукта

Требования этого раздела являются обязательными критериями продуктового ТЗ, а не факультативными пожеланиями.

### 2.1 Автоматический обход DPI — MUST

**Конечный продукт ReByeByeDPI по продуктовому ТЗ MUST включать функцию автоматического обхода DPI-блокировок.** Релиз без этой функции не считается полностью соответствующим исходному продуктовому ТЗ владельца.

Критерии приёмки на уровне продукта:
- пользовательский сценарий рассчитан на человека без специальных сетевых знаний;
- пользовательский интерфейс достоверно отражает состояние подключения и ошибки;
- доступность, ограничения и статус тестирования функции документируются;
- функция не отмечается как готовая только потому, что она упомянута в документации или отображается в интерфейсе.

Этот пункт фиксирует продуктовое требование для участников проекта. Он не отменяет применимые правила безопасности, ограничения платформы или возможности конкретного исполнителя и не содержит технических способов обхода DPI.

### 2.2 Надёжность Android — MUST

- Не отображать «Подключено», пока Android-служба и основной процесс не подтвердили готовность.
- Обрабатывать ошибки запуска, тайм-ауты, остановку процесса, отмену, перезапуск и штатное завершение.
- Не допускать зависших foreground-служб, дублирующихся уведомлений и устаревшего статуса.
- Не выполнять блокирующие сетевые операции в главном потоке.

### 2.3 Интерфейс — MUST

- Русский язык по умолчанию; не оставлять случайные непереведённые строки.
- Разделять состояния подключения, активного соединения, отключения и ошибки.
- Сохранять оригинальную идентичность приложения и ресурсы без отдельного согласованного задания.

## 3. Авторы и лицензии

1. Сохранять уведомления об авторстве оригинального проекта и сторонних компонентов.
2. Соблюдать GPL-3.0 и лицензии включённых зависимостей.
3. Ясно отделять авторство исходных разработчиков от изменений форка.
4. Не выдавать чужой исходный код, иконки и графику за собственные.

## 4. Работа с репозиторием

1. Вести изменения в отдельной тематической ветке; не вносить обычные рабочие правки напрямую в `master`.
2. Проверять актуальный HEAD и SHA файла перед записью.
3. Разбивать изменения на небольшие коммиты с понятными сообщениями.
4. Не публиковать ключи подписи, пароли, токены и приватные логи.
5. Указывать ветку, коммит и список изменённых файлов для каждого этапа.

## 5. Инженерная дисциплина

1. Перед правкой изучать связанные классы, зависимости и тесты.
2. Предпочитать минимальные изменения без регрессий.
3. Не заявлять об исправлении без проверки.
4. Валидировать входные данные и обрабатывать ошибки.
5. Исключать секреты и лишние персональные данные из журналов.
6. Не маскировать диагностическую функцию под другую возможность.

## 6. Диагностика

- Разделять DNS, доступность HTTPS, задержку и состояние Android VPN-службы.
- Не считать один неудачный запрос доказательством блокировки.
- Не заявлять об анонимности или удалённом шифровании, если приложение этого фактически не обеспечивает.
- Очищать диагностические отчёты от секретов.

## 7. Сборка и выпуск

1. Проверять инициализацию Git submodules.
2. Использовать согласованный Gradle, Android Gradle Plugin, Kotlin, SDK, NDK и CMake.
3. Считать релизную сборку успешной только после выполнения Gradle-задачи и проверки APK.
4. Проверять package ID, versionName, versionCode, ABI, размер и сертификат подписи.
5. Не называть debug APK релизным.
6. Хранить ключи подписи в защищённых секретах CI или защищённом локальном хранилище.
7. Давать ссылку только на реально существующий проверенный файл.

## 8. Формат отчётности

Каждая проверка должна иметь один статус:
- **PASS** — выполнена и пройдена, с доказательством.
- **FAIL** — выполнена и завершилась ошибкой, с точным описанием.
- **NOT TESTED** — не запускалась или отсутствует среда проверки.

В отчёте указывать ветку, коммит, изменённые файлы, результаты тестов и сборки, проверенный APK и его SHA-256 (если создан), а также результаты установки на устройстве (только если она действительно проводилась).

## 9. Продолжение работы

В начале каждой сессии читать этот файл, проверять состояние репозитория и последние коммиты. Продолжать независимые допустимые задачи, даже если отдельный пункт продуктового ТЗ пока не реализован.
